# Ideas of 2026-09-28

The day the history was made a substrate of its own to read: it follows the scope the reader stands in, it is read as prose as well as on the canvas, and it is had by a toggle over the panes rather than as a pane of its own, its canvas running left to right.

*The author's thinking, dictated 2026-09-28 and held as said; this lead is the session's, and each prompt beneath stands whole in its own place.*

## 1. The history follows the scope

There are some immediate things in how it is used that can be resolved. The first is the scope you are in, which is seen in the canvas and in the prose lane: the git view should adhere to it. So you only see the changes that apply in the holarchy in which you are placed.

*The author's, 2026-09-28, dictated.*

## 2. A canvas alone is not enough

There is an immediate problem: there is a canvas and a prose lane, and then there is a custom pane for git, which is a canvas, and that is not enough. You need to be able to see the git substrate both as canvas and as prose. You might select something in the canvas and then want to see it as prose substrate, naturally, which you can fold and look at just like the normal canvas and prose lane: something you navigate the substrate with.

*The author's, 2026-09-28, dictated.*

## 3. Two alternatives

Currently `history.md` is not mounted as part of the substrate, which it could be. The thing about the git canvas is that it is wanted to go left to right.

The first alternative is the power user approach: mount `history.md` as part of the substrate, with no custom view. When you go into `history.md`, since it links to commits, you can choose there to highlight a commit for diffing.

The other alternative is to exclude `history.md` from the substrate and make it a custom thing; but that custom thing also demands a canvas and a prose lane. So there would be a higher order of selectability. There are the widgets and their icons; then the prose lane, the canvas and the plate; and then a git toggle, which makes the prose lane and the canvas, and maybe the plate, look at the history substrate. Toggle it off, and you are looking at the normal substrate again.

Those are the two alternatives, and this needs to be understood first.

*The author's, 2026-09-28, dictated.*

## 4. The canvas runs left to right, a trunk and not a tree

The requirement is that the canvas can go left to right, with the root: the root goes left to right and the rest still descend downwards. That makes sense, because with git it is not really a tree any more. It is more just a trunk, with branches in one direction.

So either that is made a power user thing, where you can always toggle the canvas, and are then free to do it in both a history view and a normal substrate view; or it is locked, if git is made a special thing.

*The author's, 2026-09-28, dictated.*

## 5. The special thing, since mounting conflicts

The first alternative has an obvious conflict, so the second makes sense: git as a special thing, had by a toggle. Consider next how the use of it is made, with the icons and the rest, so there is a solid plan before implementation.

*The author's, 2026-09-28, typed in answer to the session's reflection, which gave the conflict as the scope: mounted, the history would be a place in the body, and standing in it the reader would no longer stand in the holarchy it is meant to filter by; and that it would reverse [history as a view apart](../ideas/history.md#2-why-it-came-out).*

## 6. A mode, a status, and the root's direction for every canvas

Good, it makes sense: the toggle moves, and it is a mode, not a pane.

For the canvas, laying the root level top down or left to right is a feature that can perhaps be had in the normal canvas as well, as a toggle; in git it just defaults to left to right. It is helpful then if folding with shift and the arrow keys works well there too.

Next to the git glyph there can perhaps be a simple status, so that you know whether a range or a commit is selected. That needs visibility, for it affects everything.

The plate stays the body, always. That is fine for now, and a different solution for managing the windows can be considered later.

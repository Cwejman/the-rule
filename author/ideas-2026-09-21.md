# Ideas of 2026-09-21

The day git was taken up again, to lay its foundation properly this time: a shallow and a deep set of data, commits at a granularity that does not conflate, a substrate of their own that tells stories over runs of them, and what a reader sees of them from where they stand.

*The author's thinking, dictated 2026-09-21 and held as said; this lead is the session's, and each prompt beneath stands whole in its own place.*

## 1. The foundation is laid properly this time

What is needed with git integration has been attempted before, and with some mistakes, so this time the foundation is laid more properly. If such a foundation can be laid, the technical issues of last time are not had.

*The author's, 2026-09-21, dictated; the attempt before is [reading the substrate as a diff](../ideas/history.md).*

## 2. A shallow set and a deep set

What is started with is a shallow data set on git, and a complete one. The shallow is for understanding which commits exist, and the like. The deep holds all of the diffs a commit contains.

*The author's, 2026-09-21, dictated.*

## 3. The deep set is had per commit

The deep one perhaps needs to be paginated, or really had per commit, and made available that way.

*The author's, 2026-09-21, dictated.*

## 4. Cached locally, files when published

Running locally, that might mean it is cached in some way. Published, as with the pipeline, it really is that the pipeline puts this data out as available files, the author thinks.

*The author's, 2026-09-21, dictated.*

## 5. Not embedded as the substrate is, unless the shallow is light

So it might not be wanted to embed it as JSON, as is done with the substrate. Maybe the shallow piece is embedded, depending on whether it is felt to take a lot of data. If it does not, perhaps it is there, and then each commit might be retrievable on its own.

*The author's, 2026-09-21, dictated; "I don't know" is his, on each commit being retrievable.*

## 6. No endpoint to query, and only so many files at once

It cannot be an API endpoint where things are queried specifically. And the other way round, making it into separate files, given that only so many files can be retrieved in parallel, might be a problem. These are some of the thoughts the author is having.

*The author's, 2026-09-21, dictated; open.*

## 7. Commits at a granularity that does not conflate

With that foundation in place, commits need to be at the appropriate granularity so as not to conflate things. This has been covered in the author's holon, though he does not know exactly where it is told.

The essence: making a file in which only briefs are added can all be one commit. Adding and editing that are of separate purpose is not as bad. But several edits conflated is bad, the author thinks, and several sessions conflated is really bad. Exactly where the line is drawn he does not know.

An interaction with a specific piece for one purpose, and an interaction with another piece of the holarchy, conflated, is not favourable, unless there is a really strong and common theme to the change: something changes and it propagates into the field. Great. So it is important to have enough granularity in working with the commits.

*The author's, 2026-09-21, dictated; what he recalls as covered may be [a prompt stands alone](ideas-2026-09-16.md#21-a-prompt-stands-alone) and [atomicity](ideas-2026-09-16.md#22-atomicity), which the session has not confirmed with him.*

## 8. Bloat is valuable information, and is solved by something else

Within a session the commits sometimes feel to the author as if they bloat. Maybe an agent has been run thirty times to build a feature, because feedback was given on feedback on feedback. But that is also valuable information.

The commits tell a story, in their atomicity and in their interaction with the specific piece. So the bloating is solved by something else, not by fewer commits.

*The author's, 2026-09-21, dictated.*

## 9. How a change affected the field

This was discovered in the previous git integration, the one reverted. The author wants to be able to see how a certain change has affected the field: the minimap greyed out, and what was affected coloured. Or looking at a commit and seeing the actual holons it affected, as links, and being able to go there. And in the lane itself, seeing the change in place.

*The author's, 2026-09-21, dictated; "process lanes" in the recording is read as the lane.*

## 10. Commits are one level, and the low one

The problem is that commits are just one level, and they are the low level. It is not enough to put these commits in a branch and group them so they are easily selectable.

*The author's, 2026-09-21, dictated.*

## 11. A substrate for commits

Various layers of substrate are needed. There is definitely going to be a specific substrate: the same substrate, but a specific place in it, which has to do with commits. It has a specific practice for how its briefs relate to the commit SHAs, so that the author can make comments on any series of commits.

*The author's, 2026-09-21, dictated.*

## 12. Stories told over runs of commits

Whether a series can be spread out he does not know; it might always have to be an actual sequence. What happens is that he might talk about the last three commits, and the session adds a comment about those three. Then it might be thought that the last ten have something specific to do with each other that he wants to comment on, and the ten before those are something else.

So stories can be told, and a certain number of commits grouped by them.

*The author's, 2026-09-21, dictated; whether a series must be contiguous is open.*

## 13. The canvas, with the commits at the bottom

The author would then like to view it on the canvas: left to right, with the commits at the bottom and the assembled groups seen on top of them, so stories are told like that.

*The author's, 2026-09-21, dictated.*

## 14. Partition, or many directions

The question is whether it always has to partition, so that it can be viewed as a directed graph. Or whether various directions are possible, multi-dimensional, which the author is not sure we are ready to do.

*The author's, 2026-09-21, dictated; open.*

## 15. A selection shows the pieces affected

Even further: depending on the selection made, pressing a commit, or a brief that holds ten commits, the actual pieces affected are seen on the canvas as well.

*The author's, 2026-09-21, dictated.*

## 16. The address shows only the commits that affect it

Depending on the address you are in, you only see the commits that affect it. That is also a reason commits with a local purpose should not go all over the place: then they are seen locally, at what you are doing there, and a commit that pertains to many other things is not what you see when you are looking there.
